# Database deadlock triage — v2

Updated 2026-05-12 in response to incident PI-2026-05-12. Supersedes the
rb04 entry in `runbooks/rb04_db_deadlock_triage.md`. Linked here so future
on-calls can find the canonical procedure during a deadlock incident.

## Detection

Page on `pg_stat_activity.deadlock_detected_count` exceeding 1 per minute on
any production database. The previous threshold of 1 per second was far too
permissive — the May 2026 incident sustained 8 deadlocks per minute for 4
minutes before any alert fired.

## Containment

When a deadlock detector triggers, identify the longest-held lock holder via
`SELECT pid, query, application_name, age(query_start) FROM pg_stat_activity
WHERE state = 'active' ORDER BY age(query_start) DESC LIMIT 10;`. If the
holder is a migration script, prefer rolling back the migration over killing
the connection: the rollback releases the lock and allows queued waiters to
drain cleanly.
